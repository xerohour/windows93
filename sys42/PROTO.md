# sys42 static-hosting prototype — findings

**Question:** can the real sys42 desktop (github.com/windows93dotnet/sys42, MIT)
from Windows93's creators boot as a plain static site (GitHub Pages, no backend)?

**Answer: yes, with 6 small patches — and the "backend" turns out not to be a
backend at all.** Everything below was verified against sys42 at the clone in
`~/workspace/.w93-src/sys42` (depth-1, 2026-10-20). Nothing was copied from
windows93.net; the prototype is built only from the MIT sys42 repo.

Prototype root = this directory. **876 files, 9.6 MB total.** Serve it with any
static server from this directory as site root, then open `/desktop/`:

```sh
cd ~/workspace/windows93-sys42-proto && python3 -m http.server 8932
# http://localhost:8932/desktop/
```

## 2. What `client.connect()` actually does — the "backend" is a service worker

`src/desktop/desktop.js` line ~24 is `await client.connect()` before rendering.
Reading `src/42/os/network/client.js`: connect() does **not** open any network
backend connection. It:

1. Registers the service worker at `/42.sw.js` (`{type:"module"}`).
2. If the SW is active but not yet controlling, reloads the page once.
3. Otherwise waits for `controllerchange`.
4. Sends `42_SW_HANDSHAKE` over an IPC bus to the SW; the SW replies with its
   config (`vhost`, `dev`) — see `src/42/os/network/service.js`.

The SW (`service.js`) is the OS's file server: it intercepts same-origin
fetches and serves files from the virtual FS drivers by consulting the file
index, and on install it downloads `/42-kits/<version>.tar.gz` into a cache
(`service/kit.js`; a 404 there is handled gracefully — `if (!res.ok) return`).
It calls `skipWaiting()` + `clients.claim()`, so first-load control works.

**Is connect() failure fatal? Yes, upstream:** it's an unguarded top-level
await — if registration throws (unsupported browser, blocked SW) or the
controller never arrives, the module never finishes and the desktop never
renders (blank page). But nothing after it actually *needs* the SW:

- The virtual FS (`src/42/core/fs.js`) defaults `/` to the **IndexedDB**
  driver — fully client-side. Other drivers in-tree: memory, localstorage,
  sessionstorage, ipc, filesystemaccessapi. Real hosted files are read via
  the "fetch" driver using the file index.
- The desktop folder, taskbar, apps manager and windows all run off the FS
  API directly, not through SW-served URLs. The SW adds: kit caching,
  serving virtual files as URLs, and the vhost sandbox proxy.

So the minimal static patch is: **register with a relative URL, race a
timeout, and continue booting on failure** (patch P2 below).

## 3. Patches applied (all marked `STATIC PROTO PATCH` in the files)

| # | File | Change | Why |
|---|---|---|---|
| P1 | `42.sw.js` | Import `./42/…` instead of `/42/…`; `vhost` derived from `self.location` instead of hardcoded `http://localhost:3000/…`; `dev: true → false` | Absolute paths + a localhost vhost break anywhere except the dev machine; dev mode expects the dev server (live-reload/cache-bust) that static hosting doesn't have |
| P2 | `desktop/desktop.js` | `await client.connect()` → try/catch + `Promise.race` 5 s timeout + `client.connect({url: "../42.sw.js"})` | Upstream await is fatal/hangs on SW failure; relative URL is subpath-safe; desktop works without the SW (§2) |
| P3 | `42/core/fs/FileIndex.js` | `new URL("/files.cbor", import.meta.url)` → `new URL("../../../files.cbor", import.meta.url)` | Absolute path breaks under a subpath (Pages project site); this file sits at `<root>/42/core/fs/` |
| P4 | `42/os/network/service/kit.js` | `` fetch(`/${kitsFolder}/…`) `` → `fetch(new URL(…, location.href))` | Same subpath issue; kit.js only runs inside the SW, whose location is `<root>/42.sw.js` |
| P5 | `desktop/index.html` | `href="/style.css"` → `"../style.css"` | Subpath-safety |
| P6 | `index.html` (landing) | `/style.css`, `/42/ui/head.js`, `/desktop/`, `/tests.html`, `/` → relative equivalents | Subpath-safety (the tests page itself is not in the prototype) |

Everything else is byte-identical to upstream. All patched files pass an ES
module parse check (`vm.SourceTextModule`).

**Known subpath limitation (not patched, needs a decision before Pages
deployment):** inside the SW, `service.js` matches `new URL(e.request.url)
.pathname` against file-index paths — under a subpath (e.g.
`/windows93/sys42/…`) the pathname carries the prefix and SW file-serving
misses (plain network fetch still works, so hosted files still load; only
SW-served *virtual* files are affected). Root deployment (custom domain /
user site root) avoids this entirely. A fix would strip
`self.registration.scope`'s pathname prefix in `serve()`/`proxy()`.

- **Static serving:** `python3 -m http.server` over the prototype —
  `/`, `/desktop/`, `/style.css`, `/42.sw.js`, `/files.cbor`,
  `/42-kits/0.0.0.tar.gz`, theme CSS, `desktop.js`, app manifests, fixture
  files: **all 200**.
- **Module graph trace:** starting at `desktop.js` + `42.sw.js`, fetched and
  followed every static/dynamic import literal: **418 modules, zero genuine
  misses.** The only 404s were (a) two commented-out imports my tracer
  picked up (`themesManager.js`, `tree.js`), (b) `ExecutionContext.js` in
  `42/core/dev/testing/` whose imports point at a stale layout — dev/test
  only, never loaded by the desktop, and (c) regex artifacts.
- **No bare specifiers** in the boot graph (no importmap/bundler needed).
- **Headless boot: could not be verified in this environment.** jsdom 30
  does not execute `<script type="module">` (page loads, body stays empty,
  no errors — a jsdom limitation, not a sys42 one). The local Chromium
  (Chrome 152) **blocks loopback navigation by policy**
  (`ERR_BLOCKED_BY_LOCAL_NETWORK_ACCESS_CHECKS`, and "Your organization
  doesn't allow you to view this site" for browser-initiated loads) — the
  same loopback block previously hit with the browser tool. So the desktop
  render itself (taskbar/folder in a real browser) remains **unverified
  until it is deployed to a public https URL** — which is also exactly the
  GitHub Pages target environment (https + SW allowed). First-load
  expectation from the code: SW installs → one automatic reload (upstream
  behaviour in connect()) → desktop renders; if the SW is unavailable, P2
  logs `[static-proto] Booting without service worker: …` and renders
  anyway.

- **Dev tooling** (watch/live-reload, tests page, kit rebuild) stays with
  the dev server.
- The desktop folder still points at the *test fixtures* folder — a real
  deployment should repoint it (one line in `desktop.js`) or seed a proper
  `$HOME/desktop/` in IndexedDB.

## 7. How apps work in sys42 (for wiring SkiFree/Bytebeat/JSNES next)

**Discovery:** `42/os/managers/appsManager.js` does
`fileIndex.glob("**/*app.json5")` at startup and registers every hit — an
app is **any folder containing `app.json5`**, and it must appear in
`files.cbor`. The Start menu is `os.apps.makeMenu()` over this registry;
launch is `os.apps.launch(name)` / clicking a file whose mimetype the app
claims via `decode.types`.

**Manifest (`app.json5`, JSON5):**

```js
{
  name: "TextEdit",            // required, unique — registry key
  command: "textedit",         // CLI command name
  categories: ["utilities"],   // Start-menu grouping
  description: "…",
  width: 300, height: 300,     // default window size
  decode: { types: [ { description: "Text", accept: ["text/*"] } ] },
  // one of the following content sources:
  $ref: "./app.js",            // JS entry (TextEdit; also has index.html)
  modules: "./Hydra.js",       // JS entry (Hydra test app)
  content: [ /* declarative UI plan */ ],   // ImageViewer, MediaPlayer — no JS needed
  document: "{{$files/0/path}}", inset: true, // Sandbox: render a file in a sandboxed frame
}
```

**Icons:** auto-discovered by `classes/App/normalizeManifest.js` from
`<appdir>/icons/icon-16.png`, `icon-32.png` (160px variants are generated at
preinstall for PWA use); a bare `icon-32.png` next to the manifest also
works (Sandbox/Hydra style).

**Apps in this prototype (5):**

| App | Location | Style |
|---|---|---|
| TextEdit | `42/os/apps/TextEdit/` | `$ref` app.js + index.html, textarea editor |
| ImageViewer | `42/os/apps/ImageViewer/` | declarative `content` plan |
| MediaPlayer | `42/os/apps/MediaPlayer/` | declarative, `ui-player` |
| Sandbox | `42/os/apps/Sandbox/` | `document` + `inset` — opens HTML files sandboxed |
| Hydra | `tests/apps/Hydra/` | `modules: "./Hydra.js"` — **the real Hydra** from the creators, hiding in their test fixtures |

**Wiring an external program (SkiFree / Bytebeat / JSNES) afterwards:**
add `programs/<name>/app.json5` next to its existing `index.html` with a
Sandbox-style manifest (`document` pointing at the program's page,
`inset: true`, an `icon-32.png`, name/categories/width/height), then
regenerate `files.cbor` (§4). No framework code changes needed — the same
pattern the Sandbox app uses for arbitrary HTML. One caveat to test after
deployment: sandboxed apps run through the vhost/SW path, so verify on the
public URL; a non-inset variant (window with an iframe-style document) is
the fallback if the sandbox realm misbehaves on Pages.

## Addendum (2026-10-20, after first live deployment) — Patch P7

The first live test at `https://xerohour.github.io/windows93/sys42/desktop/`
rendered the desktop/taskbar but every app manifest fetched from the
**origin root** (`/42/os/apps/TextEdit/app.json5` → 404), icons were broken
images, and no app would launch. Root cause: fetch-backed files (file-index
inode `0`) were fetched and exposed by their raw FS path (`/42/...`), which
is only a valid URL when the deployment root is the origin root.

**P7** adds a deploy-root resolver (`fsPathToURL`) computed from each
module's own `import.meta.url`, applied at all three sites that turned FS
paths into URLs:

- `42/core/fs/BrowserDriver.js` — `open()` (fetch on read) and `getURL()`
  (icon/image URLs)
- `42/os/classes/App/FileAgent.js` — the `url` getter for app files

At a domain root the resolution is identical to upstream behaviour, so the
patch is safe for the creators' own deployment too. The service worker's
virtual-file serving still matches raw pathnames (see §5 limitation); under
a subpath those requests simply fall through to the network, where P7's
URLs are correct.

## Addendum 2 (2026-10-20) — Patch P8

Live retest after P7: manifest 404s were gone, but the desktop still threw
`TypeError: The "path" argument must be a string: undefined` once per icon
and icons had no artwork/labels. Cause: several framework spots convert
real URLs to FS paths via `new URL(..., import.meta.url).pathname`, which
under a subpath keeps the deploy prefix (`/windows93/sys42/42/...`) while
the file index is keyed without it (`/42/...`). Theme icon lookups
therefore missed and returned `undefined` into `fs.getURL()`, and app
manifests got an origin-root `dirURL`, which would have 404'd every app's
`$ref`/modules on launch.

P8 adds one shared, import-free helper — `42/core/fs/fsPathToURL.js` —
exporting `fsPathToURL` (FS path → deploy-correct URL) and `urlToFsPath`
(URL → FS path, stripping the deploy prefix), both derived from the
helper's own location so they are identity mappings at a domain root.
Applied in: BrowserDriver (now re-exports the helper), FileAgent,
normalizeManifest (manifestURL + icon srcs), themesManager (icon theme
dirs), appsManager (decode-type icon linking), and App.prepareManifest
(string manifest paths). P7's three call sites now route through the same
helper.

## Addendum 4 (2026-10-20) — Patch P9

A phone report showed Chrome's "ServiceWorker script at
https://xerohour.github.io/42.sw.js for scope https://xerohour.github.io/
encountered an error during installation" dialog. The desktop page has
always registered the worker relatively (verified in every deployed
commit), but three other root-absolute worker references existed in the
tree, and two fragilities could surface as install errors:

- `42/os/network/client.js` — the connect() **default** was "/42.sw.js";
  now resolved relative to the module (any no-arg caller gets the right
  worker under any deployment root).
- `42/os/network/client/vhost.html` — registered "/42.sw.js?proxy"; now
  "../../../42.sw.js?proxy".
- `demos/ui/vhost.demo.html` — called client.connect() with no URL (the
  one call site that produced exactly the reported root script+scope);
  now passes "../../42.sw.js". Its stylesheet link was likewise
  root-absolute and is now relative.
- `42/os/network/service.js` — the install handler awaited kit.install()
  unguarded: a failed kit download (749 KB tar over a flaky connection)
  failed the entire SW installation, which Chrome reports as an
  installation error. Kit install is now caught — it is only a cache
  warm-up.
- `42/ui/components/sandbox.js` — every app window's head hardcoded
  href="/style.css" (origin root → 404 under a subpath); now resolved
  from import.meta.url like the head.js URL next to it.

**Kit rebuild (same addendum):** the root cause of the recurring
mixed-version behaviour all day: `42-kits/0.0.0.tar.gz` was a snapshot
of the framework from prototype time, and the service worker serves
kit-cached files whenever the cache key matches — so browsers kept
running pre-P7 framework code (old BrowserDriver, old sandbox.js) no
matter what was deployed. The kit was rebuilt from the current tree
(861 entries: every indexed file except `42-kits/`, `42.sw.js`,
`LICENSE`, `tests/`) and the version in `42.sw.js` bumped to `0.0.1`,
so `activate()` purges the old cache on every existing browser.
**Any future framework patch must rebuild the kit and bump the version,
or browsers will keep serving the snapshot.**

## Addendum 10 — Patch P11: heal persisted pre-P8 theme configs, kit 0.0.7 (2026-10-20)

Bug report (user's phone): sys42 desktop renders teal + taskbar, but every
desktop icon is an empty box (no art, no label) under a cascade of TypeError
dialogs — `The "path" argument must be a string: undefined`. Fresh-profile
probes (including the 0.0.5 round's probe_p12) all passed, so this shipped.

Root cause (reproduced locally, probe_poison.mjs): the poison is not in any
kit — it is in the profile's persisted FS. A first boot writes the manager
defaults to `$HOME/.theme.json` (ConfigFile `reset()` → `save()`), and later
boots load the stored value verbatim. Profiles created by the pre-P8 build
(the original 80ca0ff deployment) stored
`icons: ["/windows93/sys42/42/themes/default/icons"]` — a URL pathname
carrying the deploy prefix. P8 fixed the DEFAULTS only. With the stored
value, `findIconPath` misses the FileIndex (keys are prefix-free FS paths),
the octet-stream fallback misses too, `themesManager.getIconPath` returns
undefined, and `Icon.getInfos` calls `fs.getURL(undefined)` →
`assertPath` TypeError, once per icon, on every boot. Kit bumps could never
fix it; only the framework's Format Disk / `?clear-site-data` wipe could,
because that clears the persisted config. Seeding exactly that legacy value
into a healthy profile reproduced the screenshot precisely (37 icons,
0 images loaded, 10 TypeError dialogs); fresh profiles stay clean.

Fix (Patch P11, `42/os/managers/themesManager.js`, marked in code):
- `postload()` maps stored `icons` entries through the P8 `urlToFsPath`
  (idempotent for correct entries, strips the deploy prefix from legacy
  ones) and persists the healed config via `save()` when anything changed.
- `getIconPath()` applies the same normalization defensively to each theme
  path (and the fallback) before lookup.

No other persisted config carries an FS path built from a URL pathname
(appsManager/mimetypesManager checked; themesManager `style`/`module` are
URL-space and correct as pathnames).

Kit rule (P9) followed: files.cbor regenerated (1,018 leaves; only delta is
the kit swap), kit rebuilt as 42-kits/0.0.7.tar.gz (968 files; content diff
vs 0.0.6 is exactly the patched themesManager.js), 42.sw.js version bumped
"0.0.6" → "0.0.7" so existing browsers purge the old cache, 0.0.6 tar
deleted, everything synced to ~/workspace/windows93-sys42-proto/.

Verification: see the fix report — poisoned-profile upgrade test (0.0.6
profile with the legacy config, then 0.0.7 served) plus fresh-profile

## Addendum 11 — Patch P12: merge-missing file index + app registry, kit 0.0.8 (2026-10-20)

Bug report (user's phone, after P11): the TypeError cascade is gone, but
"no apps show up" — the desktop shows only the original sample
files/folders and the Start menu only the 5 framework apps, despite 37
shortcuts and 23 registered apps in the current build. Fresh profiles
test clean, so — like P11 — this is persisted profile state, one layer
down.

Mechanism (traced in code): the desktop is a `ui-folder` over
`/tests/fixtures/formats/` whose items come from
`fileIndex.readDir()` (folder.js `getItems`), and the Start menu is
`appsManager.makeMenu()` over the registry in `$HOME/.apps.json`. Both
sit on the FileIndex, and the FileIndex is a `Storable`
(`42/core/fs/FileIndex.js`): its IndexedDB `Database` is version 1
(the `version: Date.now()` line in Storable is commented out), so its
`populate()` — the fetch + flatten of `files.cbor` — runs **only when
the store is first created**. Later boots load the persisted snapshot
verbatim. A profile created by the first deployment (80ca0ff) therefore
holds an 876-leaf index with no `.desktop` shortcuts (they arrived in
Addendum 5) and no app manifests beyond TextEdit/ImageViewer/
MediaPlayer/Sandbox/Hydra — forever, immune to kit updates, because
nothing ever re-read `files.cbor`. Second trap of the same class:
AppsManager is a ConfigFile whose `populate()` (glob `**/*app.json5`
→ register) only runs on `reset()`, i.e. when `$HOME/.apps.json` is
absent; the stored registry's version stamp is `-Date.now()` at save
time, so `load()`'s obsolete-version branch can never fire later. Even
a healed index would have left the Start menu frozen at 5 apps.
Audit of the other seeded-once state: themesManager (static defaults;
path form healed by P11), mimetypesManager (static FILE_TYPES
populate; app associations are re-added by `appsManager.add()`),
the kit Cache Storage (version-keyed, handled by the bump rule) — no
other index-derived content is persisted.

Reproduced locally (probe_legacy.mjs): a profile seeded from a
legacy `files.cbor` (876 leaves: fixture folder without the 23
`.desktop` files, only the 5 original manifests) plus the pre-P8
theme poison, booted against 0.0.7, shows exactly the report —
14 fixture icons, 5 apps, zero errors — on every load.

Fix (Patch P12, marked in code):
- `42/core/fs/FileIndex.js` — in `init()`, after loading the persisted
  index, fetch the current `files.cbor` (the existing `populate()`)
  and add every leaf that is missing locally, with its hosted inode
  (0). Existing entries are never touched, so user-created files
  (array inodes) are preserved; idempotent; a failed fetch leaves the
  persisted index as-is.
- `42/os/managers/appsManager.js` — new `postload()`: register any
  indexed `app.json5` whose path is not represented in the stored
  registry (via the existing `add()`), persisting once if anything
  was added. Per-manifest failures are settled, never fatal.

Kit rule (P9) followed: kit rebuilt as 42-kits/0.0.8.tar.gz (968
files; content diff vs 0.0.7 is exactly the two patched files),
42.sw.js version bumped "0.0.7" → "0.0.8", 0.0.7 tar deleted,
files.cbor regenerated (1,018 leaves; only delta is the kit swap),
tree synced to ~/workspace/windows93-sys42-proto/.

Verification: see the fix report — legacy-profile upgrade (transitional
load unchanged, next load 37/37 icons + 23 apps, TextEdit and BananaMP
launch, stable across reboots with no duplicates), fresh-profile
two-load test, local and live.
